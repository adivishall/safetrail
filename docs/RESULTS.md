# Results — the single source of truth for every number

Every benchmark figure quoted anywhere in this repository comes from here, and
this page comes from one command:

```bash
make bench          # writes bench/results/*.csv and prints the tables below
```

Nothing on this page is typed by hand into prose and left to rot. If a number in
the README, the presentation, or the viva prep disagrees with this file, **this
file wins** and the other is a bug. The numbers below are a representative run
(Apple clang `-O2`, one laptop, `-ffp-contract=off`); they move a few percent
run to run, which is why timings are the **median of 7 passes after a warmup** and
why the CSVs also carry the best run and the spread.

> **Read every number with three caveats.** (1) The tourists are **simulated** —
> real OpenStreetMap geography, simulated people, on purpose (simulation is what
> gives ground truth). (2) Every speedup is a ratio to **our own brute force**, the
> correctness oracle, not to an external library. (3) At small `n` the times are
> sub-microsecond and dominated by noise; the honest headline is always the
> largest-`n` row.

## 1. The headline — three spatial indexes, same data, same queries

`make bench` §1 — 450 m query box, 2000 probe queries per row, median of 7.

| zones | brute force | quadtree | R-tree (STR) | quadtree gain | R-tree gain | candidates/query | spread |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 10 | 0.07 µs | 0.07 µs | 0.06 µs | 1.0× | 1.1× | 0.01 | ±39% |
| 100 | 0.24 µs | 0.09 µs | 0.08 µs | 2.7× | 2.9× | 0.10 | ±174% |
| 1,000 | 2.75 µs | 0.10 µs | 0.11 µs | 28.4× | 25.1× | 0.97 | ±72% |
| 5,000 | 10.96 µs | 0.31 µs | 0.22 µs | 35.8× | 50.6× | 4.90 | ±47% |
| 10,000 | 22.86 µs | 0.64 µs | 0.30 µs | 35.6× | 76.0× | 9.81 | ±40% |
| 20,000 | 49.26 µs | 1.35 µs | 0.40 µs | 36.6× | 122.5× | 19.86 | ±52% |
| 50,000 | 118.98 µs | 3.45 µs | 0.67 µs | 34.5× | 176.6× | 49.37 | ±15% |
| **100,000** | **243.68 µs** | **6.95 µs** | **1.00 µs** | **35.0×** | **244.1×** | **98.78** | **±9%** |

Brute force is visibly linear. **The candidate count is identical across all three
indexes** — they return the same true positives, so the speedup ceiling is output
size `k`, exactly as `O(log n + k)` predicts. This is the most important academic
result in the project: *at 100,000 dense zones, ~99 zones genuinely overlap each
450 m query, and no index can return fewer answers than exist.* The R-tree wins
not by returning less but by visiting fewer nodes to find the same answers.

**On run-to-run variation.** The quadtree settles around **~35×** at scale and is
stable. The R-tree's 100k figure is the most volatile number in the project —
observed between **~240× and ~260×** across runs — because it is the fastest
absolute time (≈1 µs) and so the most sensitive to scheduler noise. Quote it as a
band, not a constant. The largest-`n`, lowest-spread rows are the honest headline;
the small-`n` rows are noise (see the ±spread column) and are not meaningful.

Chart: [`bench/plots/index_scaling.svg`](../bench/plots/index_scaling.svg) (log–log,
regenerated by `tools/plot_scaling.py` from the CSV).

## 2. Correctness — every fast index vs the brute-force oracle

`make bench` §2. This is the experiment that makes every speedup above trustworthy.

| density | queries | true hits | quadtree mismatches | R-tree mismatches |
|---:|---:|---:|---:|---:|
| 50 zones | 6,000 | 1,257 | **0** | **0** |
| 500 zones | 6,000 | 13,307 | **0** | **0** |
| 5,000 zones | 6,000 | 135,282 | **0** | **0** |

**18,000 randomized queries across three densities, zero mismatches.** Seeds are
fixed (see `apps/safetrail_bench.cpp`); geometry is the shared ray-casting
predicate. The unit suite adds a second layer: every fast structure is checked
against a brute-force oracle inside its own `*_test.cpp`.

Ray casting vs winding number (`make bench` §4): **100,000 points against 200
polygons, 0 disagreements** between the two independent point-in-polygon
implementations.

## 3. R-tree bulk loading — STR vs repeated insertion

`make bench` §9. Same data, same query code; only the way the tree was assembled
changes.

| zones | insert build | STR build | insert nodes | STR nodes | insert µs/query | STR µs/query | query gain |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | 0.2 ms | 0.1 ms | 214 | 155 | 0.16 | 0.09 | 1.81× |
| 10,000 | 2.1 ms | 1.3 ms | 2,133 | 1,456 | 1.29 | 0.25 | 5.20× |
| 50,000 | 12.8 ms | 7.7 ms | 10,684 | 7,259 | 4.19 | 0.70 | 6.00× |
| 100,000 | 27.8 ms | 17.0 ms | 21,368 | 14,383 | 5.98 | 0.97 | **6.17×** |

Both are `O(n log n)`. STR produces a **33% smaller tree** with far less envelope
overlap, so a query descends fewer branches. This is the cleanest "the structure,
not the machine" result in the repository.

## 4. Persistent quadtree — path copying vs full copies

`make bench` §5. The advanced structure: keep every historical version cheaply.

| versions | nodes allocated | nodes if full-copied | sharing | query@past | query@now |
|---:|---:|---:|---:|---:|---:|
| 51 | 523 | 1,903 | 3.6× | 0.09 µs | 0.10 µs |
| 201 | 2,582 | 14,633 | 5.7× | 0.15 µs | 0.16 µs |
| 1,001 | 14,025 | 158,257 | 11.3× | 0.35 µs | 0.40 µs |
| 5,001 | 71,314 | 930,257 | **13.0×** | 1.16 µs | 1.51 µs |

Two results: **sharing improves as history grows** (3.6× → 13.0×), and **querying
the past costs the same as querying the present** — no replay, just a different
root pointer. A validity-only change allocates **zero** new nodes (asserted in
`tests/index/versioned_index_test.cpp`).

## 5. Interval tree — AVL deletion under churn

`make bench` §13. The one structure on the query path with a *guaranteed* bound.

| live size | height fresh | height after churn | stab µs fresh | stab µs churned | delete µs |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 12 | 12 | 0.013 | 0.012 | 0.124 |
| 10,000 | 16 | 16 | 0.254 | 0.238 | 0.176 |
| 50,000 | 19 | 19 | 2.544 | 2.466 | 0.216 |

Height stays at the AVL bound for the **live** size even after churn — the
tombstone version this replaced froze height at the high-water mark. Deletion is
logarithmic even though a tenth of the entries share each low endpoint, thanks to
the total `(low, high, value, seq)` key.

## Operational number (running simulation, real dataset)

From the exact `make dashboard` configuration, so it is reproducible:

```
./build/safetrail_headless --zones data/zones/shillong_osm.geojson \
    --tourists 60 --hours 2 --synthetic 400
```

Pruning reduces the loaded zone set to a few candidates per query
(≈100×+ reduction). The figure moves with zone count, zone size, and how fast the
population is walking, so it is quoted with its configuration or not at all.

## Test suite

`make test` — **39 test files, ≈770 assertion sites, 11,616 individual checks
executed** in a representative run (many assertions run inside randomized loops, so
the runtime check count is far higher than the number of `ok(...)`/`near(...)`
call sites). Zero failures. Every fast structure is checked against a brute-force
oracle. The whole suite is clean under UBSan locally and under AddressSanitizer +
UBSan in CI.

## Determinism

`make determinism` — same seed, two runs, byte-identical output. Guaranteed by a
fixed-seed PRNG, explicit tie-breaks in every ordered structure, and
`-ffp-contract=off`. The one documented boundary: two libm implementations
(Apple's vs glibc) differ in the last ulp of `asin`/`sin`/`cos`, which moves the
dispatch travel totals by ~3% across operating systems but leaves the evaluation
core (events, Merkle root, alerts, index stats) byte-identical. See the README's
"Determinism" section.
