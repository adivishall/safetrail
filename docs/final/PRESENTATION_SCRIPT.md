# Presentation script (14 slides; about 8 minutes, with the live demo after slide 11)

Slide numbers match `docs/final/SafeTrail_final_presentation.pptx`. Speaker
notes in the deck carry the same text.

**1. Title — SafeTrail.** "SafeTrail is a geofencing and incident-response
system for tourist safety in low-connectivity regions, built on hand-written
data structures in C++17."

**2. The problem.** "In the hills around Shillong, cliffs, rivers and closed
roads are where people get hurt, and phones lose signal exactly there. Help is
late when nobody knows who is where. Checking every position against every
hazard zone is O(n) per GPS fix — the cost the whole design is about."

**3. What it does.** "People opt in. Every fix is checked against hazard
zones, with GPS uncertainty treated as a disc, not a point. Transitions become
alerts, related alerts become incidents, the nearest responder is routed along
roads, groups that split are noticed, phones that go offline keep working and
sync later, and everything is kept in a tamper-evident history."

**4. Architecture.** "Three layers: the engine — indexes, geometry, the
evaluator; the platform — users, consent, sessions, alerts, incidents, groups,
responders, history, offline sync; and a single-threaded HTTP server with a web
console. No database, no map service, no dependencies."

**5. The core structures.** "Brute force as the oracle; a quadtree that splits
space; an R-tree that groups items, bulk-loaded with STR; an AVL interval tree
for validity windows; a persistent quadtree for every past version."

**6. Supporting structures.** "A binary heap for Dijkstra, A* and alert triage;
union-find with rollback for groups and incidents; an open-addressing hash
table for users, sessions and sync; a timer wheel for escalation; a ring buffer
for recent fixes; a k-d tree for snapping to the road network; a Merkle tree
for evidence."

**7. Results.** "At 100,000 zones in one district the R-tree answers 224 times
faster than a scan, the quadtree 33 times — identical answers. At constant
density, where only about one zone overlaps each query, the speedups reach
about 550× and 1,000×. STR packing makes the R-tree 6× faster than building it
by insertion; A* settles about 75 % fewer junctions than Dijkstra."

**8. Multi-user.** "Through the whole platform a fix costs about 3 microseconds, and that cost does not change from 10 users to 5,000 — about 300,000 fixes a second on one core, roughly 7 KB per tracked person. The same benchmark found a real bug: alert bookkeeping was quadratic until alerts were indexed per user."

**9. Correctness.** "Every fast structure has an oracle; invariants are
checked after every operation; 51 test files, 12,137 checks; 28 injected bugs,
all caught; byte-identical output on macOS and Linux."

**10. Privacy.** "Opt-in only, nobody else can switch it on, stop any time,
history expires and can be erased, every look at someone's location is
audited, responders see a person only while assigned."

**11. Live demo** — switch to the browser ([LIVE_DEMO_SCRIPT.md](LIVE_DEMO_SCRIPT.md)).

**12. Syllabus map.** "Arrays and ring buffers, stacks, trees and recursion,
BSTs and AVL rotations, augmented trees, hashing with collision handling, heaps
and priority queues, graphs and adjacency lists, Dijkstra and A*, union-find,
binary search, complexity and measurement. Beyond: persistence, Merkle proofs,
Lamport clocks, computational geometry."

**13. Limitations and future.** "Simulated people; an in-memory server that
runs on this laptop — the public link is only a static replay; the OSM hazard
polygons are thin, so 'uncertain' is often the honest answer; benchmarks from
one laptop. Next: persistence, real GPS traces, a phone app running the same
offline evaluator, public hosting behind TLS, and Argon2."

**14. Close.** "Thank you — the code, tests, benchmarks and this deck are in
the repository, and every benchmark figure on these slides is regenerated by
`make bench`."
