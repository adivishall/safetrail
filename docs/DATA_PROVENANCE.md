# Data Provenance

Where every number in the dashboard comes from, and how it reaches the page.
Written to be re-verifiable: every claim below has a command under it.

**Short answer:** the dashboard performs **zero network requests**. There is no
transmission at all — the data is serialised by the C++ engine and embedded
directly into the HTML file at generation time, as a JavaScript object literal.

---

## 1. What the dataset actually is

Two categories, and it matters that they are not confused.

### Real, fetched input

`data/zones/shillong_osm.geojson` — 38 zones whose geometry is **real
OpenStreetMap data**, fetched from the Overpass API for the area around Shillong,
Meghalaya (bbox 25.50–25.72 N, 91.78–91.98 E). These are actual reservoirs,
lakes, forests, and a waterfall cliff at their true coordinates, including named
tourist landmarks like **Wards Lake** and **Sonapani Waterfall Cliff**.

The fetch-and-convert pipeline is reproducible:

```bash
# 1. fetch (the Overpass query is in tools/, HTTP POST to overpass-api.de)
curl -s -X POST -d @tools/overpass.ql https://overpass-api.de/api/interpreter -o /tmp/osm.json
# 2. convert OSM ways -> validated GeoJSON zones
python3 tools/osm_to_zones.py
```

`tools/osm_to_zones.py` classifies each OSM feature into our zone schema (water →
caution, quarry/cliff → restricted, forest → advisory), simplifies the boundary
with Ramer–Douglas–Peucker, and **drops any polygon that is self-intersecting,
degenerate, or too small** — because `ZoneStore::load_geojson` rejects the whole
file on the first invalid polygon (GAP 10). Of 96 real closed rings fetched, 38
survive selection and validation.

```bash
python3 -c "import json;d=json.load(open('data/zones/shillong_osm.geojson'));print(json.dumps(d['features'][1]['properties'],indent=1))"
```

```json
{
 "name": "Wards Lake",
 "kind": "caution",
 "severity": 4,
 "osm_id": 131468994,
 "source": "OpenStreetMap",
 "active_from_s": 1800,
 "active_to_s": 5400,
 "rule_note": "spillway discharge window"
}
```

Coordinates are real Meghalaya positions (25.52–25.74 N, 91.78–92.01 E) in
GeoJSON `[lon, lat]` order, carrying the originating `osm_id` and
`"source": "OpenStreetMap"` on every feature.

The older `data/zones/meghalaya.geojson` (8 hand-drawn zones) is kept as a small
fixture but is no longer the default dataset.

### Simulated input

- **Tourists.** No real people. Positions are generated by the mobility models in
  `sim/mobility.cpp` (random waypoint, route following, with pauses).
- **GPS error.** Injected by `apply_gps_error()` — 4 m open sky, 35 m multipath at
  25% probability, 2% dropout. These are the measured regimes cited in
  [GAP_ANALYSIS.md](GAP_ANALYSIS.md).
- **Synthetic filler zones.** Procedurally generated polygons (400–5000 depending
  on the run), present only to give the spatial index a realistic workload at
  scale. Rendered as faint density so they do not compete with the real zones,
  and tagged `syn:1` in the export so nothing confuses them with real geography.

**This split is deliberate.** The *geography* is real — fetched from OpenStreetMap,
so the zones are genuine hazards at genuine coordinates. The *tourists* are
simulated, because no real tourist-tracking dataset exists for this problem and
simulation is what provides *ground truth*: we know exactly where every tourist
truly was, so we can measure whether the engine got the answer right. A recording
of real GPS traces would not let us do that.

### What is genuinely computed

Everything between input and output. The geometry, the spatial indexing, the
three-valued containment, the hysteresis filtering, the correlation, the group
connectivity, the persistent index. None of it is stubbed, mocked, or precomputed.

## 2. The pipeline, hop by hop

```
data/zones/shillong_osm.geojson           real OSM geometry on disk
        │
        ▼  util::Json::parse_file()               src/util/json.cpp
   hand-written JSON parser, no library
        │
        ▼  ZoneStore::load_geojson()              src/fence/zone.cpp:53
   ├─ strip_closing_vertex()                      src/fence/zone.cpp:84
   │    GeoJSON repeats the first vertex; our rings are implicitly closed,
   │    so keeping it creates a zero-length edge
   ├─ Polygon::validate()                         src/fence/zone.cpp:97
   │    self-intersecting geometry is REJECTED, never stored  [GAP 10]
   └─ Validity{active_from_s, active_to_s}        [GAP 3]
        │
        ▼  Simulator::reindex()                   src/sim/simulator.cpp:19
   ├─ SpatialIndex::build()      quadtree / R-tree, root fitted to data
   └─ VersionedIndex::add_zone() one version per zone   src/sim/simulator.cpp:63
        │
        ▼  Simulator::step()   ×7200 ticks
   mobility → GPS error → Evaluator::evaluate_all()
   → containment, hysteresis, transitions → Events
        │
        ▼  TraceRecorder::capture(s)              apps/safetrail_headless.cpp:86
   one frame per 10 s of simulated time: positions, accuracy, confirmed state
        │
        ▼  TraceRecorder::write_html()            src/viz/html_export.cpp:282

        │
        ▼

```

## 3. How it reaches the page: it doesn't travel

There is no client-server split, no API, no socket. `write_html()` builds one
string and writes one file.

### Byte accounting

```bash
python3 -c "
h=open('dashboard.html').read(); i=h.index('const D = '); j=h.index(';\n', i)
print('total file        %9d bytes' % len(h))
print('embedded data     %9d bytes (%.1f%%)' % (j-i-10, 100*(j-i-10)/len(h)))
print('html+css+js shell %9d bytes' % (len(h)-(j-i)))"
```

```
total file          1643399 bytes
embedded data       1631641 bytes (99.3%)
html+css+js shell     11748 bytes
```

The page is 99.3% data. The viewer is 11.7 KB of hand-written HTML, CSS and
canvas JavaScript.

### Proof of zero network activity

```bash
for p in 'fetch(' 'XMLHttpRequest' 'WebSocket' 'EventSource' '<script src' '<link' 'https://' 'http://'; do
  printf '%-18s %s\n' "$p" "$(grep -c -F "$p" dashboard.html)"; done
```

```
fetch(             0
XMLHttpRequest     0
WebSocket          0
EventSource        0
<script src        0
<link              0
https://           0
http://            0
```

No fetch, no XHR, no socket, no external script, no stylesheet link, no CDN, no
tile server, no font import, no analytics beacon. **Open it with `file://` on a
machine with the network physically disabled and it behaves identically.**

### Why this architecture

Not laziness — it is the same constraint the project is about. Existing
implementations of `SIH25002` need a live round trip to PostGIS to answer a
containment question, which fails precisely in the terrain the problem statement
targets (see GAP 6). A dashboard that needs a tile server to draw a map has the
same defect at demo time. So the map is drawn on a canvas from the polygon
coordinates we already hold, and the whole thing is one file.

## 4. Proof the numbers are engine output, not literals

### Every displayed field traces to an engine getter

```bash
grep -oE 's\.(zones|tourists|events|index|counters|correlator|summary|versioned|now_ms)\(\)' src/viz/html_export.cpp | sort -u
```

```
s.correlator()   s.counters()   s.events()   s.index()
s.now_ms()       s.summary()    s.tourists() s.versioned()   s.zones()
```

There are no hardcoded statistics in the exporter. `pruning` is computed as
`zones / avg_candidates`, not typed in.

### Different seed, different results

```bash
for seed in 111 222; do ./build/safetrail_headless --tourists 30 --hours 1 \
  --synthetic 400 --seed $seed --show 0 | grep "zone entries"; done
```

```
seed 111:  zone entries  159
seed 222:  zone entries  143
```

### Same seed, byte-identical output

```bash
./build/safetrail_headless --seed 111 --export-html /tmp/a.html >/dev/null
./build/safetrail_headless --seed 111 --export-html /tmp/b.html >/dev/null
cmp /tmp/a.html /tmp/b.html && md5 -q /tmp/a.html
```

```
22f683bf36aa0a97c4ae110f7a0551ee
```

Determinism holds, which is what makes the replay harness and the hysteresis A/B
comparison valid at all.

### The trace contains real values, not placeholders

```bash
python3 -c "
import re,json
d=json.loads(re.search(r'const D = (\{.*?\});\n',open('dashboard.html').read(),re.S).group(1))
f=d['frames'][40]
print('lat[:4]  ', f['lat'][:4])
print('accuracy ', sorted(set(f['acc'])))
print('versions ', d['versions'], 'sharing', d['sharing'])"
```

```
lat[:4]   [25.51757, 25.52218, 25.52496, 25.51701]
accuracy  [4.0, 35.0, 999.0]
versions  909  sharing 13.79
```

The accuracy set is exactly the three regimes the GPS model produces — 4 m open
sky, 35 m multipath, 999 m dropout — and nothing else. If these were fabricated
they would not land on precisely those three values.

## 5. The investigation view  [GAP 3]

The persistent index is not decoration; the dashboard queries its history.

Zone validity windows in the authored dataset:

| zone (real OSM feature) | in force | illustrative rule |
|---|---|---|
| Sonapani Waterfall Cliff | always | permanent restriction |
| Wards Lake | 00:30 → 01:30 | spillway discharge window |
| Love Jungle | 00:45 → end | landslide risk after rainfall |
| all others | always | permanent |

The geometry is real; the validity *windows* are illustrative operational rules
layered on top, so the GAP 3 time-travel demo has something to show. That
distinction is stated in the file's `metadata.note`.

Scrubbing the timeline re-answers "what were the rules at this moment":

- **at 00:01** — Wards Lake (spillway window 00:30–01:30) and Love Jungle
  (landslide window opens 00:45) read *not in force* and render as dashed ghosts.
- **at 00:53** — both are in force; the earlier ghosts have become solid.
- **at 01:36** — Wards Lake has dropped back out (window ended 01:30) while Love
  Jungle stays in force to the end.

Verify by scrubbing, or non-visually:

```bash
python3 -c "
import re,json
d=json.loads(re.search(r'const D = (\{.*?\});',open('dashboard.html').read(),re.S).group(1))
def at(ms): return [z['name'] for z in d['zones'] if not z['syn']
                    and ms>=z['from'] and (z['to']<0 or ms<z['to'])
                    and (z['from']>0 or z['to']>=0)]
print('time-varying zones in force at 00:01:', at(60000))
print('time-varying zones in force at 00:53:', at(3180000))"
```

The **zone change log** panel is rendered from
`VersionedIndex::changes_between()` — the same changelog an incident
investigation would query, not a re-derivation in JavaScript. The counters panel
reports the retained version count and node-sharing ratio, read from
`share_stats()`.

Crucially, the evaluator consults the *same* `Validity` objects each tick
(`src/fence/evaluator.cpp`), so a zone out of force generates no transitions at
all. The display and the engine cannot disagree, because there is one source.
