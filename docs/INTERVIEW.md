# Interview guide

The spoken companion for a **software / technical interview** (not the academic
viva — that's [VIVA.md](VIVA.md), and the examiner's-eye version is
[PROFESSOR_REVIEW.md](PROFESSOR_REVIEW.md)). Every number here traces to
[RESULTS.md](RESULTS.md), which is generated by `make bench`. If RESULTS.md and
this file ever disagree, RESULTS.md wins.

Anchor sentence:

> **The spatial index finds the candidates; the geometry determines the answer.
> I hand-built both, measured every fast index against a brute-force oracle so a
> speedup can't hide a wrong answer, and the interesting result is that the
> speedup has a ceiling I can explain — output size `k`, exactly as `O(log n + k)`
> predicts.**

---

## 30-second version

"SafeTrail decides, repeatedly over time, whether tourists are inside, outside,
or uncertain relative to geographic hazard zones. The naive way checks every
zone against every tourist every tick — at 100,000 zones that's hundreds of
millions of geometry ops. I built spatial data structures by hand — a quadtree
and an R-tree — that prune those 100,000 zones to the ~99 actually near each
tourist, then run exact point-in-polygon on just those. Everything is
hand-written C++17, no spatial library, because the data structures are the
point."

## 60-second version

Add correctness and the honest ceiling:

"The speedups are real — ~35× for the quadtree and ~240–260× for the R-tree at
100,000 zones against my own brute force — but the number I actually care about
is that they're *correct*: 18,000 randomized queries across three densities,
zero mismatches against the brute-force oracle. A fast wrong answer is worthless.
And I can explain the ceiling: all three indexes return the same candidate count
because those are true positives, and no index can return fewer results than
exist — so the ceiling is output size `k`. My design doc first guessed ~29,000×;
measurement disciplined it to ~35×, and understanding *why* is worth more than
the big number would have been. On top of the spatial indexes there's an interval
tree for zones that turn on and off over time, and a persistent version of the
quadtree so I can ask what the map looked like at any past moment."

## 3-minute version

Problem → scaling wall → three-stage solution → proof → the one advanced piece.

1. **Problem.** Repeated geofencing: many hazard polygons, a stream of location
   updates, and you must decide containment *and* boundary crossings continuously.

2. **Why naive fails.** Brute force is `O(n)` per query — linear in zone count —
   so cost grows without bound as zones are added. That's the wall.

3. **The solution is three data-structures problems stacked.**
   - *Spatial pruning:* a tree returns only zones near the tourist (`O(log n + k)`).
   - *Temporal filtering:* an AVL interval tree answers "which zones are in force
     at time `t`?" in guaranteed `O(log n + k)` — the one structure on the hot
     path with a real worst-case bound, because it balances on data, not space.
   - *Exact geometry + state transition:* ray casting gives a 3-valued
     inside/outside/uncertain answer for the few candidates, and an event is
     emitted only when containment *changes*.

4. **How I proved it.** Correctness before speed: every fast index is validated
   against brute force (18,000 queries, 0 mismatches; plus ray-casting vs an
   independent winding-number implementation, 100,000 points × 200 polygons, 0
   disagreements). Then the benchmark is a median of 7 passes, each speedup a
   ratio to my own oracle, and every number lives in one generated file.

5. **The advanced piece.** A persistent (path-copying) quadtree: each mutation
   copies only the `O(depth)` nodes on one root-to-leaf path and shares every
   untouched subtree by reference count. Measured 13.0× structural sharing at
   5,001 versions, and querying the past costs the same as querying the present —
   just a different root pointer. That's the incident-investigation feature.

---

## 5 strongest technical decisions

1. **Keep brute force as a permanent deliverable, not a throwaway.**
   `BruteForceIndex` stays behind the same interface forever: it's the correctness
   oracle every fast index is validated against, and the denominator of every
   speedup. This is what makes the speedups trustworthy rather than decorative.

2. **Benchmark a quadtree *and* an R-tree on identical data.** They make opposite
   trade-offs — partition space (disjoint cells) vs partition items (overlapping
   envelopes). Measuring both on the same workload shows the R-tree's STR bulk
   packing winning by ~7× at scale, and lets me explain *why* (a 33% smaller tree
   with less envelope overlap descends fewer branches). *(RESULTS.md §1, §3)*

3. **STR bulk-load the R-tree instead of repeated insertion.** Same asymptotic
   build cost (`O(n log n)`), but STR produces a 33% smaller tree and a 6.17×
   faster query at 100,000 zones — "the structure, not the machine". *(§3)*

4. **Balance the interval tree on data (AVL), so the temporal filter has a
   *guaranteed* bound.** Under churn its height stays at the AVL bound for the live
   size — the tombstone version this replaced froze height at the high-water mark.
   Deletion stays logarithmic via a total `(low, high, value, seq)` key. *(§5)*

5. **Make determinism non-negotiable and document its exact boundary.** Fixed
   seeds, explicit tie-breaks in every ordered structure, `-ffp-contract=off` →
   byte-identical output, gated by `make determinism`. The one honest exception —
   dispatch travel totals move ~3% across OSes because Apple's vs glibc `asin`
   differ in the last ulp — is documented, not hidden.

## 5 hardest engineering problems (and the resolution)

1. **Path copying that actually shares.** Getting a persistent quadtree to copy
   only the touched path and share the rest by refcount — and *proving* the
   sharing (13.0× at 5,001 versions; a validity-only change allocates zero new
   nodes, asserted in `versioned_index_test.cpp`) rather than assuming it.

2. **The speedup ceiling.** The design doc predicted ~29,000×; the measured number
   is ~35×. Rather than "fix" the benchmark, I worked out that the candidate count
   is identical across indexes because those are true positives — the ceiling is
   `k`, the output size. Explaining the gap is the real result.

3. **Point-in-polygon edge cases.** Vertices, collinear points, and boundary
   grazes are where ray casting silently gives wrong answers. Handled explicitly
   and cross-checked against an independent winding-number implementation
   (100,000 × 200, 0 disagreements). *(GEOMETRY_EDGE_CASES.md)*

4. **AVL interval-tree deletion under heavy churn** when a tenth of entries share
   a low endpoint — solved with a total ordering key so deletes stay logarithmic
   and height tracks the *live* set, not the high-water mark.

5. **Rollback union-find for group cohesion** (an extension): splits *and* merges
   means no path compression, so unions stay undoable — a genuinely different DSU
   from the textbook one.

## 5 likely interviewer questions

**Q: Why hand-write these instead of using Boost.Geometry / PostGIS / STL?**
It's a data-structures project — the structures are what's being graded and
learned, so building them is the point, not a production recommendation. I say
that explicitly. `std::vector`/`std::string` are allowed as raw storage;
`std::sort` is an algorithm; `std::shared_ptr` is the memory management the
persistent index's sharing genuinely needs. Everything with structure — trees,
heaps, hash tables — is mine.

**Q: Quadtree or R-tree — which is better?**
Neither universally; they trade off oppositely. The quadtree partitions space
into disjoint cells and is simple and stable (~35× at scale). The R-tree
partitions items into overlapping bounding envelopes; STR-packed it visits fewer
nodes and wins ~7× — but its 100k timing is the most volatile number in the
project (~240–260×) because it's the fastest absolute time (~1 µs) and most
sensitive to scheduler noise, so I quote it as a band, not a constant.

**Q: Your speedup is "only" 35× — I'd expect more from a tree over 100k items.**
That's the most interesting result. All three indexes return the *same*
candidates because they're true positives, and at 100k dense zones ~99 genuinely
overlap each query. No index can return fewer answers than exist, so the ceiling
is output size `k`, exactly `O(log n + k)`. The tree can't beat the amount of
real work; it just stops doing the fake work brute force does.

**Q: The tourists are simulated — doesn't that undermine the results?**
Real OpenStreetMap geography, simulated people, on purpose: simulation is what
gives me ground truth to validate correctness against. The benchmark is about the
data structures' behaviour on a defined workload, not a claim about real tourist
movement. I state that caveat up front.

**Q: How do you know a fast index never returns a wrong answer?**
Two layers. Every fast structure is checked against the brute-force oracle inside
its own unit test, and the benchmark runs 18,000 randomized queries across three
densities with zero mismatches. Correctness is validated before any speedup is
reported — that ordering is deliberate.

## Honest limitations (state these unprompted)

- **Simulated tourists** (real geography, synthetic movement) — ground truth by
  design, not a field study.
- **Speedups are vs my own brute force**, the oracle — not vs an external library.
- **The R-tree 100k figure is a band (~240–260×)**, not a constant — smallest
  absolute time, most scheduler-sensitive.
- **Small-`n` rows are noise** (see the ±spread column); only the largest-`n`,
  lowest-spread row is the honest headline.
- **Cross-OS determinism has one documented boundary** (~3% on dispatch travel
  totals from libm `asin` differences); the evaluation core stays byte-identical.
- **Hand-written structures are a learning constraint**, explicitly not a
  production recommendation over mature spatial libraries.
