# Deployment guide

SafeTrail has two different things on the internet, and they are easy to
confuse: the **integrated application** (the C++ server with accounts, live
multi-user tracking, alerts, incidents, dispatch and the Data Structures Lab),
publicly hosted on Render's free plan, and the **static dashboard** (one HTML
file replaying a headless run), on GitHub Pages and Vercel. This guide says
what each one is, how it was deployed, what the free hosting does and does not
give, and how to run everything locally. Deployed and checked on 2026-11-02.

| | What it is | Where it runs | Accounts, live data, API |
|---|---|---|---|
| 1. Integrated application | `safetrail_server` + the web console, in public-demo mode | **https://safetrail-v0bh.onrender.com** (Render free web service, Singapore) | yes; accounts are held by the project owner |
| 2. Static dashboard | a replay produced by `safetrail_headless`, embedded in one HTML file | https://adivishall.github.io/safetrail/ and https://safetrail-adivishall.vercel.app | none |
| 3. Local application | the same server on your own machine | http://127.0.0.1:8080 | yes; passwords printed in your terminal |

## 1. The public application (Render, free plan)

### 1.1 What a visitor gets

The sign-in page, with this notice under the button: *Public demonstration.
Every tourist here is simulated; no real person is tracked. Everything resets
when the server restarts or wakes from sleep, so nothing you enter is kept.
Accounts are issued by the project owner.* The top bar carries the tag
**public demo · resets**. There is no self-registration: the four accounts
(`admin`, `operator`, `responder`, `tourist`) have random passwords that only
the owner can read (§1.4). After sign-in it is the same console as the local
one, with the walkthrough scenario loaded and paused at T+00:00:00.

The world is shared. Everyone signed in works in the same simulation, and an
operator or administrator who presses Run, Reset or loads another scenario
does it for everyone. Every person in it is simulated (named `SIM · …`,
badged SIM); the six responders are fixtures (`Demo …`, badged DEMO). No real
location is ever collected: the console never asks the browser for one
(`Permissions-Policy` denies geolocation), and every position comes from the
scenario scripts.

### 1.2 The service

Created from the Blueprint [render.yaml](../../render.yaml) in the owner's
Render workspace (Hobby plan, no payment method on file, no other services),
and confirmed in the Render Dashboard after creation:

| Setting | Value |
|---|---|
| Service | web service `safetrail`, Blueprint-managed |
| Plan | **Free** |
| Region | Singapore (Southeast Asia), the closest to India |
| Source | `adivishall/safetrail`, branch `final/product-completion` |
| Runtime | Docker, [Dockerfile](../../Dockerfile) at the repository root |
| Health check | `/api/health` (unauthenticated; exempt from rate limits) |
| Auto-deploy | on every commit to the branch (confirmed: a push went live 47 s later) |
| Build filter | commits that change only `docs/**` or Markdown files do not redeploy, since none of them is in the image and every redeploy resets the shared world |
| Secrets | `SAFETRAIL_ADMIN_PASSWORD`, `SAFETRAIL_OPERATOR_PASSWORD`, `SAFETRAIL_RESPONDER_PASSWORD`, `SAFETRAIL_TOURIST_PASSWORD`, each generated by Render (`generateValue`: a random 256-bit value) |
| URL | https://safetrail-v0bh.onrender.com |

With no card on file, nothing can be charged: if the workspace ever exceeds a
free allowance, Render suspends the service instead of billing.

### 1.3 The image

[Dockerfile](../../Dockerfile), two stages on Ubuntu 24.04:

1. **build** — installs g++ and make, compiles `build/safetrail_server` with
   `-Werror`, strips it (about 16 s on Render's builder).
2. **run** — a fresh Ubuntu 24.04 with only the stripped server, `web/app/`,
   the two OpenStreetMap files the server loads
   (`data/zones/shillong_osm.geojson`, `data/osm/roads.txt`) and the committed
   benchmark CSVs (`bench/results/`, served read-only to the Analytics page).
   No compiler, sources, tests or Git history; [.dockerignore](../../.dockerignore)
   keeps documents, build output, local state and `.env*` out of the build
   context. 148 MB; runs as the unprivileged user `ubuntu` (UID 1000).

The start command:

```
/app/safetrail_server --host 0.0.0.0 --public --client-ip-header CF-Connecting-IP \
  --pbkdf2-iterations 10000 --var /tmp/safetrail $SAFETRAIL_ARGS
```

- `--host 0.0.0.0` and `$PORT`: Render routes to the port in `PORT` (10000 by
  default; the image sets the same fallback). TLS is terminated by Render's
  proxy, which redirects `http://` to `https://`.
- `exec` makes the server PID 1, so Render's SIGTERM on a redeploy reaches it;
  it closes its listener, prints `stopped.` and exits 0 (0.2 s measured).
- `$SAFETRAIL_ARGS` adds options without a rebuild, e.g. `--scenario entry`
  (set it in the service's Environment tab).

### 1.4 Public mode (`--public`)

| Behaviour | Why |
|---|---|
| Refuses to start unless all four `SAFETRAIL_<ROLE>_PASSWORD` variables are set, each at least 16 characters; the error names the missing variables, never a value | no default or guessable account on the internet |
| Never generates, prints or writes a password; no `var/demo-credentials.txt`; the log lists the accounts as `(from environment)` | the platform's log is visible to anyone with dashboard access |
| `Secure` on the session cookie (with `HttpOnly; SameSite=Strict`), and `Strict-Transport-Security: max-age=31536000` | the cookie never travels over plain HTTP |
| Client address from `CF-Connecting-IP`, believed only when the connection comes from a private (proxy) address and the header appears exactly once; otherwise the socket address | throttling per real visitor, not per proxy |
| Rate limits (§1.5) and the three-level sign-in lock | one visitor cannot exhaust a 0.1-CPU, single-threaded server, and nobody can lock everyone else out |
| PBKDF2 at 10,000 iterations instead of 120,000 | on the free instance one 120,000-iteration hash took 3.7 s with the whole server waiting; the four passwords are 256-bit random values, for which the iteration count adds nothing |
| Loads the walkthrough scenario paused at T+00:00:00 on every start | a visitor who wakes the service gets a known, explainable state |

The owner reads a password in the Render Dashboard: service **safetrail** →
**Environment** → the variable's copy or reveal button. To change one, edit
the value there (16+ characters) and save; Render redeploys, and the new
value applies after the restart.

### 1.5 Limits on requests

| Limit | Applies to | Over the limit |
|---|---|---|
| 100 requests/s per client address, burst 300 | every request except `/api/health` | 429, `Retry-After: 1` |
| 2 API requests/s per address without a session, burst 20 | anonymous `/api/...` | 429 |
| 20 API requests/s per session, burst 60; a Lab run costs 5 | signed-in `/api/...` | 429 |
| 2 sign-ins/s for the whole server, burst 10 | `POST /api/login` | 429, `Retry-After: 2` |
| 10 failed sign-ins from one address | that address | locked for 5 min |
| 5 failed sign-ins for one account from one address | that account, from that address only | locked for 60 s |
| 25 failed sign-ins for one account from all addresses | that account | locked for 60 s |

The per-account-and-address lock means a wrong password locks only the person
typing it; the per-account lock still bounds guessing spread across many
addresses. A count starts again after 15 minutes without a failure.

### 1.6 What the free plan means

| Property | Consequence |
|---|---|
| Spins down after 15 minutes without traffic | the next visit wakes it and waits while it starts. Measured on 2026-11-02: after 18 idle minutes the instance had stopped (its log ends with `stopped.` 15 minutes after the last request); the next request took 13.5 s while a new instance started (the server builds its world in 1.3 s of that), and the ones after it 0.2–0.3 s. Render allows up to about a minute. |
| Memory only, ephemeral filesystem; may be restarted at any time | **every restart, redeploy or wake starts a fresh world**: scenario progress, alerts, incidents, the evidence log, sessions and any accounts or zones created in the console are gone. Only the four passwords persist (they are environment variables). Nothing here is durable history. |
| One instance, 0.1 CPU, 512 MB | the server uses about 38 MB; the slowest request (a full scenario reset) took 3.9 s under the same limits locally; pages poll once a second |
| 750 free instance-hours a month per workspace | enough for one service running all month |
| Shared public URL | anyone can reach the sign-in page; only holders of a password get further |

Persistence (accounts, zones and evidence on disk, signed Merkle roots) would
need a paid disk or database, which this deployment deliberately does not
use; see [LIMITATIONS_AND_FUTURE_SCOPE.md](LIMITATIONS_AND_FUTURE_SCOPE.md).

### 1.7 Live smoke test (2026-11-02, on the public URL)

Without an account, by script (44 of 44 passed):

- `http://` answers 301 to `https://`; the certificate verifies; `/api/health`
  answers `{"ok":true,"mode":"demo","public":true}`.
- The console and every file it names load; HSTS, CSP,
  `X-Frame-Options: DENY`, `nosniff` and `Referrer-Policy: no-referrer` present.
- `/api/session` reports a public client address, not the proxy's. A spoofed
  `X-Forwarded-For`, `X-Real-IP`, `True-Client-IP` or `Forwarded` header does
  not change it; a spoofed `CF-Connecting-IP` is refused by Cloudflare itself
  (403, error code 1000) before reaching the server.
- All 16 data endpoints answer 401 without a session; `POST` without the CSRF
  header answers 403; a wrong sign-in answers 401 and sets no cookie;
  four path-traversal forms are refused.
- 45 concurrent anonymous requests: 23 answered, 22 refused with 429 and
  `Retry-After: 1`; `/api/health` stayed 200; the limit recovered after a pause.

Signed in as `admin` in a browser (the owner typed the password):

- Session over HTTPS; the session cookie is invisible to page scripts
  (`HttpOnly`).
- Overview: 38 zones, 6 responders, 20 users (16 simulated tourists, the
  `tourist` account and three staff).
- Walkthrough at 10×: 16 tourists tracked live; paused at T+00:08:36 with 14
  alerts of 7 kinds (approaching, uncertain, zone breach, signal lost, dwell
  exceeded, group split, stationary) and 3 open incidents; later run to its end
  at T+00:15:00.
- Incident #1 (SIM · Ravi, inside the restricted *Rockfall closure*, severity
  5): acknowledged, then assigned to the recommended Demo Medical Unit A —
  1.54 km by road over 131 junctions, A* settling 772 junctions where Dijkstra
  needs 5,557 — with the route drawn on the map.
- Data Structures Lab: all 15 experiments ran (every `/api/lab/...` request
  200); the index experiment returned the same 16 zones from brute force,
  quadtree, both R-trees and geohash.
- 447 requests in the session with no failure apart from the owner's one
  mistyped sign-in (401), which was also the only console error.
- Found and fixed: between 760 and about 1,050 px wide the Reset button slid
  under the signed-in name in the top bar (commit 5f203c3, redeployed
  automatically).

After a cold start (18 idle minutes, same day):

- The first request took 13.5 s. The woken instance held a fresh world:
  walkthrough paused at T+00:00:00, no alerts or incidents, and the owner had
  to sign in again.
- Signed in: the walkthrough at 60× ran to its end with 16 tourists tracked,
  28 alerts of 8 kinds (now including a straggler), 3 incidents and the
  offline phone's sync report; incident #1, unacknowledged for 120 s, had
  escalated to severity 5, and was acknowledged and dispatched with the same
  1.54 km route.
- The Lab's index and graph experiments gave the same results as before the
  restart; the top bar at 936 px showed the fix (no overlap); no console error.

### 1.8 Operating it

| Task | How |
|---|---|
| Deploy a change | push to `final/product-completion`, or **Manual Deploy** on the service page. To follow `main` after the merge, set `branch: main` in `render.yaml` and the Blueprint's branch in Render |
| Roll back | service → **Deploys** → an earlier deploy → **Rollback**; or revert the commit and push |
| Watch it | service → **Logs** (application output) and **Events** |
| Stop it | service → **Settings** → **Suspend Web Service**; resume the same way |
| Start over elsewhere | in any Render workspace: **New → Blueprint**, pick the repository and branch, **Deploy Blueprint**; Render reads `render.yaml` and generates the passwords |

Locally, the same image runs without Render:

```bash
docker build -t safetrail .
```

```bash
docker run --rm -p 10000:10000 -e SAFETRAIL_ADMIN_PASSWORD -e SAFETRAIL_OPERATOR_PASSWORD -e SAFETRAIL_RESPONDER_PASSWORD -e SAFETRAIL_TOURIST_PASSWORD safetrail
```

(with the four variables exported in your shell, 16+ characters each), then
open http://localhost:10000 in Chrome or Firefox, which treat `localhost` as a
secure origin and so keep the `Secure` session cookie. For an everyday local
demonstration §3 is simpler.

## 2. Static dashboard

`make dashboard` runs the engine headless over the OpenStreetMap zones with
simulated walkers and writes `dashboard.html`: a self-contained page with the
map, the replayed events and the committed benchmark table. It has no server
behind it, no accounts and no live data (`/api/health` on these hosts answers
404).

| URL | Built from | Who can open it |
|---|---|---|
| https://adivishall.github.io/safetrail/ | `main`, by `.github/workflows/deploy.yml` (job `deploy`, after every gate) | anyone |
| https://safetrail-adivishall.vercel.app | `main`, by Vercel's Git integration running `tools/vercel_build.sh` | anyone |
| https://safetrail-git-final-product-completion-adivishall.vercel.app | this pull request's branch | **only signed-in members of the Vercel project**; anyone else gets Vercel's login page (deployment protection on previews) |

Both pipelines are unchanged by the Render deployment. Details:
[../DEPLOYMENT.md](../DEPLOYMENT.md).

## 3. Local application (the fallback that needs no network)

Everything in the live demo also runs on one laptop, with no network, no
account anywhere and nothing to pay for.

On a MacBook Air M4 (macOS, Apple clang):

```bash
xcode-select --install
```

```bash
git clone https://github.com/adivishall/safetrail.git
```

```bash
cd safetrail && make app
```

The first build takes about a minute. The server prints the four accounts
(`admin`, `operator`, `responder`, `tourist`) with generated passwords, saves
them in `var/demo-credentials.txt` (mode 0600, git-ignored), loads the
walkthrough scenario paused at T+00:00:00, and serves the console at
**http://127.0.0.1:8080**. To choose the passwords instead:

```bash
SAFETRAIL_ADMIN_PASSWORD='choose-10+-chars' SAFETRAIL_OPERATOR_PASSWORD='choose-10+-chars' make app
```

Before presenting, prove the build end to end (starts its own server on a
free port; about 22 s):

```bash
make e2e
```

Other modes, ports and the reset command are in
[COMPLETE_TECHNICAL_DOCUMENTATION.md](COMPLETE_TECHNICAL_DOCUMENTATION.md) §2;
fallbacks if anything fails on the day are in
[LIVE_DEMO_SCRIPT.md](LIVE_DEMO_SCRIPT.md).

Locally all state is in memory too (a restart starts a fresh world); the
server listens on loopback only and has no TLS, which is acceptable only
because nothing leaves the machine.
