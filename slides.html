01 · The problem

Know when a tourist walks into danger — in real time.

Remote Northeast India. Difficult terrain, patchy mobile coverage, tourists who don't know the local hazards:

  • landslide slopes and quarry edges
  • restricted border zones
  • deep-water lakeshores and seasonal river crossings

We took the problem — not the expected solution.

02 · The idea that defines the project

Every existing implementation hands the hard part to a database. We wrote that engine ourselves.

"Which zones are near here?"PostGIS GiST treehand-wrote the spatial index
Tamper-proof recordsEthereum contracthand-wrote a Merkle log

This makes it a data-structures project instead of a web app — and fixes problems delegating to a cloud DB can't.

03 · Why it matters — the eleven gaps (8 built)

1GPS is not a point → answer Inside / Outside / Uncertain 2Alerts fire too late → predict the crossing ("ETA 4 min") 3Zones are static → they turn on/off, and we can rewind time 4Tourists tracked alone → model groups, detect stragglers 540 alerts for one landslide → correlate into one incident 7Continuous GPS kills battery → sample by proximity to danger 8Drift fires fences constantly → hysteresis, −91% false alerts 9Ethereum for tamper-proofing → Merkle log, offline, no chain

Research + citations in GAP_ANALYSIS.md. Three more are designed, not yet built — marked honestly.

04 · How it works — plainly

Every second, for each tourist:

  • Narrow down — which zones are even near them? A tree answers without checking all of them (a book's index vs reading every page).
  • Check precisely — are they actually inside? Real polygon geometry.
  • Report only changes — "entered" / "exited", never "still inside" forever. That's a usable alert list vs a scrolling wall.

05 · How it works — technically

It all lives in one function, Evaluator::evaluate():

1. usability gate    discard noisy fixes              O(1)
2. spatial prune     100k zones → ~2 candidates  O(log n + k)  ← the point
3. temporal filter   which are in force now?          O(1)
4. exact geometry    Inside / Outside / Uncertain     O(k·V)
5. hysteresis        real crossing, or GPS jitter?    O(1)
6. transition diff   did state CHANGE? → Event        O(k)
7. prediction        heading toward a zone? → ETA     O(k·V)

Step 2 is the whole performance story. Without the index: 200 × 100,000 × 40 = 800 million ops/tick. With it: ~27,000.

07 · Three showpiece structures

  • Persistent quadtree — nodes are immutable; a change copies one path and shares the rest by reference count. Whole history for a fraction of the cost: 13× sharing across 5,000 versions. Answers "what were the rules at 14:32?"
  • Rollback union-find — groups split as well as merge, so we must undo unions → can't use path compression. Union-by-rank alone: O(log n) find, O(1) rollback. The trade-off is the analysis.
  • Merkle evidence log — every event committed to a root; inclusion proofs verify offline; consistency proofs show the log was only appended to. Ethereum's property, in 300 lines that are ours.

08 · The data is real

  • Geography: real. 38 zones from OpenStreetMap via Overpass — actual reservoirs, forests, and landmarks around Shillong (Wards Lake, Sonapani Waterfall Cliff) at true coordinates.
  • Tourists: simulated. No real tracking data exists — and simulation gives ground truth: we know where each tourist truly was, so we can measure if the engine was right.
  • Reaches the dashboard without travelling. Zero network requests. One HTML file, 99.3% data, opens over file:// with the network off.

09 · The most interesting result

We predicted a ~29,000× speedup. Measurement brought it to 33× — and explaining why is worth more than the big number.

At 100k dense zones, ~99 genuinely overlap each query. Those are correct answers — no index can return fewer results than exist. The ceiling is output size, exactly as O(log n + k) predicts.

Stating that honestly is the point. Three real bugs were caught only by the measurements — one by looking at the visualisation.

10 · Honest engineering — before you ask

  • Worst case: quadtree/R-tree are O(n) worst case (they partition space, not data). The AVL interval tree is the one with a guaranteed O(log n).
  • Scope: 23 modules built, ~13 designed-but-stubbed. Marked ◻/✅ throughout — never a stub claimed as done.
  • The tourists are simulated. Real geography, simulated people, on purpose.
  • The dashboard is a deterministic replay, not a live server.

This is a strength, not a confession — it's what separates a graded project from a sales pitch.
